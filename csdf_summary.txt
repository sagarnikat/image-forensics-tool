2. PROBLEM STATEMENT
===============================================================================
Design and develop a tool for digital forensics of images.

When an image is submitted as evidence, an investigator must answer:

  1. Is the file what it claims to be, and has it changed?
     - Hashes, magic bytes, extension agreement, timestamps.

  2. Was it edited, retouched, spliced or composited?
     - EXIF clues, Error Level Analysis (ELA), copy-move detection.

  3. Is data hidden inside it?
     - LSB plane analysis, chi-square attack, appended payload detection.

  4. Can the findings be presented in a defensible, reproducible form?
     - Structured findings, confidence, thresholds, hashes, PDF report.

Most basic tools only show metadata or only produce a heatmap. They do not
combine file integrity, metadata, pixel analysis and a final evidence report in
one offline workflow. PixelProof fills that gap.

===============================================================================
3. MOTIVATION / WHY IMAGE FORENSICS MATTERS
===============================================================================
- Photos are used as evidence in cyber-crime, insurance, journalism, legal and
  academic cases.
- Images are easy to edit with Photoshop, GIMP, Snapseed, AI tools and phone
  filters.
- Metadata can be edited or stripped in seconds.
- Social media re-encodes and removes provenance.
- A single technique is never enough: metadata can be forged, ELA can produce
  false positives, and LSB checks fail on JPEG.
- Investigators need a tool that combines multiple independent signals and
  clearly separates observation from interpretation.

===============================================================================
4. OBJECTIVES
===============================================================================
1. Verify file integrity using MD5, SHA-1 and SHA-256.
2. Detect file-type spoofing using magic bytes and extension checks.
3. Extract EXIF, GPS, XMP and PNG text metadata.
4. Detect suspicious metadata: editor tags, AI-generator tags, timestamp
   mismatches and embedded-thumbnail mismatches.
5. Detect local compression inconsistencies using Error Level Analysis.
6. Detect copy-move forgery using keypoint matching and geometric verification.
7. Detect hidden data using LSB analysis, chi-square attack and appended-payload
   scanning.
8. Combine module scores into a final verdict.
9. Generate a PDF evidence report and provide a simple UI.
10. Keep the evidence read-only and keep all derived artifacts under output/.

===============================================================================
5. PROPOSED SYSTEM OVERVIEW
===============================================================================
PixelProof is a modular, offline pipeline:

  Input image
      |
      v
  Validate and hash (read-only)
      |
      v
  Run independent analyzers:
      - file_analysis
      - metadata
      - ela
      - copymove
      - stego
      |
      v
  Each analyzer returns a standard result:
      module, status, summary, score, findings, metrics, artifacts
      |
      v
  verdict.py combines scores and findings
      |
      v
  report.py builds a PDF evidence report
      |
      v
  app.py (Streamlit) displays tabs and allows PDF download

Key design rules:
- Evidence is never modified.
- Analysis is offline; no uploads or cloud AI.
- Thresholds live in utils/config.py and are stated in the report.
- A module failure returns a structured error, not a crash.
- Findings are leads, not proof; the verdict shows supporting and contradicting
  evidence.

| upload -> validate -> run pipeline -> tabs/results -> download PDF           |
| UI only: no forensic logic and no thresholds                                  |
+------------------------------------+------------------------------------------+
                                     |

|       |              |         |        |         |                         |
|       +--------------+---------+--------+---------+                         |
|                    each returns a ModuleResult                               |
+------------------------------------+------------------------------------------+
                                     |
                                     v

| weighted score + severity + reasoning -> verdict label                       |
+------------------------------------+------------------------------------------+
                                     |
                                     v
+------------------------------- report.py (ReportLab) ------------------------+
| case ID, examiner, hashes, findings, images, verdict                         |

Data flow:
1. Upload bytes are saved exactly as received under output/cases/<case_id>/.
2. load_image() runs Pillow verify(), reopens and forces load().
3. Each analyzer receives the evidence path and reads it without writing.
4. Each analyzer returns the standard dictionary described below.
5. verdict.py combines module scores and findings.
6. report.py embeds original and derived images plus all findings.
7. Streamlit renders tabs: Overview, Metadata, ELA, Copy-Move, Stego, Report.

Standard ModuleResult contract:

{
  "module": "metadata",
  "status": "ok" | "error",
  "summary": "22 EXIF tags - Canon EOS 90D - GPS 12.9750, 77.5944",
  "score": 0.0,                 # this module's 0-100 manipulation signal
  "findings": [
      {
        "severity": "medium",
        "title": "Editing or processing software recorded",
        "detail": "Metadata names Adobe Photoshop ...",
        "confidence": 0.85,
        "tags": ["editor", "provenance"]
      }
  ],
  "metrics": { ... },           # raw facts used by the report
  "artifacts": ["output/..."]  # derived images / files
}

7. MODULE 1 - FILE ANALYSIS AND INTEGRITY (IMPLEMENTED)
===============================================================================
File: forensics/file_analysis.py

Purpose:
Identify the real file type and prove that the evidence bytes have not changed.

Features:
- MD5, SHA-1 and SHA-256 hashes of the exact evidence bytes.
- Magic-byte detection for JPEG, PNG, GIF, BMP, TIFF, WEBP and more.
- Extension vs real-format comparison.
- Double-extension detection, e.g. holiday.jpg.exe.
- Image dimensions, colour mode, frame count, file size and filesystem
  timestamps.
- Corrupt, empty, oversized and non-image files return structured errors.
- Limits: 50 MB file size, 80,000,000 pixels (decompression-bomb guard).

Why it matters:
- A hash is the integrity anchor of the report.
- A renamed file (JPEG bytes named .png) is a common trick.
- A double extension is a common malware delivery pattern.
- A corrupt file cannot be analysed reliably; report it as an error.

Findings produced:
- Signature/extension mismatch.
- Double extension.
- Unusual or uncommon container.
- Missing or unreadable pixels.
- Hashes for chain of custody.

Example:
python -m forensics.file_analysis samples/original/original_demo.jpg

Expected clean result:
status ok, score 0.0, JPEG, 1200x800, signature/extension match.

Tests: 6 (tests/test_file_analysis.py)

8. MODULE 2 - EXIF / GPS / METADATA ANALYSIS (IMPLEMENTED)
===============================================================================
File: forensics/metadata.py

Purpose:
Extract provenance clues and detect metadata that is inconsistent or written by
editing/AI software.

Features:
- Full EXIF tag extraction with ExifRead and Pillow.
- Camera make, model, lens, serial number, software, artist and copyright.
- Capture timestamps: DateTimeOriginal, DateTimeDigitized, DateTime.
- GPS conversion:
    decimal latitude/longitude
    degrees-minutes-seconds (DMS)
    altitude
    UTC time
    OpenStreetMap link
- XMP packet extraction (CreatorTool, CreateDate, C2PA fields).
- PNG text chunk extraction (parameters, prompt, Software, Comment).
- Timestamp coherence checks:
    DateTime differs from DateTimeOriginal
    digitised time before capture time
    capture time in the future
    file modified well after capture
- Editor keyword detection:
    Photoshop, Lightroom, GIMP, Snapseed, Canva, PicsArt, VSCO, etc.
- Generative-AI keyword detection:
    Midjourney, DALL-E, Stable Diffusion, ComfyUI, Firefly, etc.
- Embedded EXIF thumbnail extraction and dHash comparison with the main image.
- 150 safe, size-limited EXIF tags stored in metrics for the report.

Score examples:
- Editing software recorded                 -> score 30
- AI-generator metadata detected            -> score 60
- Embedded thumbnail does not match image   -> score 70
- DateTime differs from DateTimeOriginal    -> score 25
- Digitised time before capture             -> score 35
- Capture timestamp in the future           -> score 35

Clean sample result:
22 EXIF tags - Canon EOS 90D - GPS 12.9750, 77.5944
Camera: Canon EOS 90D, lens EF-S 18-135mm f/3.5-5.6 IS USM
GPS: 12.975, 77.594444, altitude 920 m
Score: 0

Edited metadata sample:
score 30, editor: Adobe Photoshop, DateTime mismatch.

Why it matters:
EXIF is useful corroboration, but it is easy to edit or strip. Missing EXIF is
common after social media and screenshots. An editor tag is a lead, not proof
of malicious intent.

Privacy note:
GPS is sensitive personal data. The tool stays offline and shows coordinates
plus an OpenStreetMap link; it does not perform reverse geocoding.

9. MODULE 3 - ERROR LEVEL ANALYSIS (IMPLEMENTED)
===============================================================================
File: forensics/ela.py

Purpose:
Detect local compression inconsistencies that may indicate a pasted, edited or
re-encoded region.

How ELA works:
1. Re-save the image as JPEG at a fixed quality (default 90).
2. Compare the re-saved pixels with the original pixels.
3. Take the maximum absolute difference across R, G and B.
4. Amplify the difference into a heatmap.
5. Areas that were already at the same compression level change little;
   a region pasted after the last save often changes more.

Why a naive threshold fails:
Sharp edges, texture, noise, denoising, resizing and earlier JPEG saves all
produce residuals. A clean photo can show bright mountain rims, horizons and
bushes. Automatic scoring must therefore look for compact, dense regions, not
simply "bright pixels".

Implemented detector:
1. Compute the ELA residual.
2. Average it into 16x16 blocks.
3. Robust threshold:
      threshold = max(0.50, median + 4 x MAD)
4. Local density:
      in a 9x9-block window, at least 50% of blocks must be high-residual.
      This rejects thin horizon/roof/branch edges.
5. Connected components:
      minimum 12 blocks (about 3072 px),
      minimum width and height of 3 blocks.
6. Region validation:
      mean residual inside the region >= 0.70,
      region mean / surrounding-ring median >= 2.0.
7. Score:
      score = min(95,
                  20 + 40*area_term + 25*strength_term + 10*contrast_term)

Outputs:
- ela_<stem>_heat.png       : colourised ELA heatmap
- ela_<stem>_overlay.png    : heatmap on original, regions outlined in red
- ela_<stem>_comparison.png : side-by-side original and heatmap

Verified results:
- original_demo.jpg      -> score 0.0, 0 dense regions
- edited_metadata.jpg    -> score 0.0 (metadata-only edit, pixels unchanged)
- spliced_demo.jpg       -> score 84.3, 1 dense region
                            pixel box [144,128]-[432,352]
                            mean residual 1.044, ring 0.190, contrast 5.5x
- retouched_demo.jpg     -> score 0.0 (smooth brightness/contrast edit)
- retouched_strong.jpg   -> score 0.0 (blur lowers the residual)

Important limitation:
ELA detects compression-history discontinuities, not semantic edits. A smooth
brightness change may not create a new high-frequency residual, and blurring
can lower it. A negative ELA result is not proof of authenticity.

10. MODULE 4 - COPY-MOVE FORGERY DETECTION (PLANNED)
===============================================================================
File: forensics/copymove.py
Status: Not implemented yet. Planned as the next module.

Goal:
Detect a region copied and pasted elsewhere in the same image.

Planned method:
1. Resize huge images to a safe working size (max side 900 px).
2. Extract ORB keypoints and descriptors (budget 3000 features).
3. Match descriptors with a Lowe ratio test (ratio 0.75).
4. Reject matches that are almost on top of each other (spatial distance < 30).
5. Require at least 8 matches.
6. Geometrically verify with RANSAC (3 px tolerance) to keep consistent
   translation/rotation/scale.
7. Mark matched keypoints and draw the duplicated region on an overlay/mask.
8. Fallback: block matching for flat regions where ORB finds few keypoints.

Output:
- output/copymove_results/copymove_<stem>_overlay.png
- output/copymove_results/copymove_<stem>_mask.png

Configuration:
COPYMOVE = {
    "orb_features": 3000,
    "match_ratio": 0.75,
    "min_matches": 8,
    "min_spatial_distance": 30,
    "ransac_px": 3.0,
    "max_side": 900,
}

Limitations:
- Flat sky/wall regions have few keypoints.
- Rotation/scaling can reduce matches.
- A duplicated region must be large/textured enough.

11. MODULE 5 - STEGANOGRAPHY CHECKS (PLANNED)
===============================================================================
File: forensics/stego.py
Status: Not implemented yet.

Goal:
Detect data hidden inside an image, especially LSB replacement and appended
payloads.

Planned checks:
1. LSB plane analysis:
   - Extract the least-significant bit plane.
   - Measure entropy and even/odd balance.
   - Sequential LSB replacement makes 0/1 unusually balanced.
2. Chi-square attack:
   - Compare observed even/odd value-pair frequencies with the expected
     distribution.
   - A high p-value suggests LSB replacement.
3. Appended-payload detection:
   - PNG ends with IEND.
   - JPEG ends with FF D9.
   - GIF ends with 3B.
   - Bytes after the end marker are ignored by viewers but can carry a ZIP,
     PDF or executable.
   - Extract and hash the bytes; never execute them.
4. Visual LSB plane artifact for the report.

Configuration:
STEGO = {
    "min_appended_bytes": 16,
    "lsb_entropy_threshold": 0.92,
    "chi_square_p_threshold": 0.95,
}

Important:
JPEG compression destroys most LSB payloads. LSB/chi-square checks are strongest
on PNG, BMP and TIFF. A negative result does not prove there is no steganography.

12. VERDICT + PDF REPORT (IMPLEMENTED) / STREAMLIT UI (PLANNED)
===============================================================================
Files:
- forensics/verdict.py    (implemented)
- forensics/pipeline.py   (implemented)
- forensics/report.py     (implemented)
- app.py                  (pending)

Verdict:
    weighted = sum(weight x module score) / sum(weight of modules that ran)
    final    = 0.55 x weighted + 0.45 x strongest module score

Module weights:
    file_analysis x 0.15
    metadata      x 0.20
    ela           x 0.20
    copymove      x 0.30
    stego         x 0.15

The weights are re-normalised over the modules that actually ran, so a partial
pipeline still produces a meaningful score. The blend with the strongest module
stops one strong signal from being diluted to nothing.

Guard-rails:
- A high-severity finding always lifts the score to the review band.
- Any module scoring >= 20 also lifts the blended score to 20, so a supporting
  signal is never reported as "likely authentic".

Verdict bands:
    0-19    Likely authentic
    20-49   Suspicious
    50-100  Likely tampered
    n/a     Inconclusive (no module completed)

One-command report:
    python -m forensics.report samples/tampered/spliced_demo.jpg

Options: -o PATH, --examiner NAME, --case-id ID, --no-open, --no-optional.
The PDF is written to output/reports/ and opened in the system viewer.

PDF report contents (all implemented):
- Case ID, examiner, date and tool version.
- SHA-256 digest and file facts.
- Verdict card with score, band, confidence, coverage and agreement.
- Executive summary with supporting and contradicting evidence.
- Module score table with signal bars.
- Findings with severity, confidence and source module.
- GPS and OpenStreetMap link.
- Original image, ELA comparison sheet, overlay, heatmap, EXIF thumbnail.
- Thresholds, verdict formula and limitations.
- Chain-of-custody declaration, disclaimer and reproduction commands.

Streamlit UI (pending):
- Upload image.
- Validate and persist the exact bytes.
- Run the pipeline.
- Tabs: Overview, Metadata, ELA, Copy-Move, Stego, Report.
- Download the PDF.

22. FORENSIC PRINCIPLES USED
===============================================================================
1. Never modify the evidence.
   All modules open files read-only. Derived images are written under output/.

2. Hash before and after analysis.
   SHA-256 is the primary digest. A changed hash invalidates the result.

3. Record the tool and thresholds.
   The report states the version and parameters so the result is reproducible.

4. Separate observation from interpretation.
   metrics contain raw facts; findings contain interpretations with confidence.

5. Corroborate.
   A metadata mismatch, ELA region or LSB anomaly is a lead, not a verdict.
   The final score combines independent signals.

6. Stay offline.
   No automatic reverse geocoding, cloud AI or uploads. GPS is shown as
   coordinates plus an OpenStreetMap link that the examiner opens deliberately.

7. Chain of custody.
   Document who handled the evidence, when, and what they did. The hash chain
   in the UI phase will make tampering with the audit log detectable.

23. THEORY NOTES FOR VIVA
===============================================================================
Cryptographic hashing:
A hash maps arbitrary bytes to a fixed-length fingerprint. A one-bit change
produces a completely different digest (avalanche effect). SHA-256 is used for
integrity; MD5/SHA-1 are kept only for legacy compatibility and are not
collision-resistant.

Magic bytes:
The first bytes identify the real format:
  JPEG  FF D8 FF
  PNG   89 50 4E 47 0D 0A 1A 0A
  GIF   47 49 46 38
  BMP   42 4D
The extension is only a name. Comparing magic, extension and decoder output
detects renamed or polyglot files.

EXIF:
Exchangeable Image File Format is a TIFF-style metadata block. It stores camera
make/model, lens, exposure, capture time, GPS and an embedded thumbnail. It can
be edited with ExifTool, piexif or Pillow, so it is corroboration, not proof.

JPEG compression:
JPEG splits the image into 8x8 blocks, applies DCT, quantises coefficients and
stores them with entropy coding. Quality controls the quantisation table. Every
save is lossy and leaves a compression history.

Error Level Analysis:
Re-save at a fixed quality and compare with the original. A region with a
different compression history often has a different residual. ELA is a
heuristic: texture, sharp edges, prior compression, resizing and denoising also
produce residuals.

Why dense-region filtering:
A horizon, roof edge or branch is a thin line, so its local density of
high-residual blocks is low. A pasted region is filled, so its local density is
high. This is the main reason the tool avoids flagging every sharp edge.

Copy-move forgery:
A region is copied and pasted elsewhere in the same image. ORB/SIFT keypoints
are extracted, matched with a ratio test, and geometrically verified (RANSAC).
The matched points reveal the duplicated region. Flat areas have few keypoints,
so block matching is a useful fallback.

LSB steganography:
In an 8-bit channel, the least-significant bit changes the pixel value by at
most 1 and is visually invisible. Sequential LSB replacement makes even/odd
value pairs unusually equal, which a chi-square attack can detect. It also
raises the entropy of the LSB plane. JPEG compression destroys most LSB
payloads, so this check is strongest on PNG/BMP/TIFF.

Appended data:
Many formats declare an end marker (PNG IEND, JPEG FF D9, GIF 3B). Bytes after
that marker are ignored by viewers but can carry a ZIP, PDF or executable. The
tool extracts and hashes them without executing anything.

dHash:
A difference hash resizes the image to 9x8 grayscale, compares adjacent pixels
and produces a 64-bit fingerprint. It is robust to resizing and mild
recompression, which makes it useful for comparing an EXIF thumbnail with the
main image.

Chain of custody:
A documented record of who handled the evidence, when, and what they did. The
hash chain in the UI phase will make tampering with the audit log detectable.

===============================================================================
24. LIMITATIONS
===============================================================================
- Not court-validated software. It is an educational tool, not a replacement
  for validated forensic suites.
- ELA is not proof. Strong texture, denoising, resizing and repeated JPEG
  compression create false positives.
- ELA misses some edits. A smooth brightness/contrast change does not create a
  new high-frequency residual, and blurring lowers it. Small pasted objects can
  fall below the 12-block minimum area. A negative ELA result is not proof of
  authenticity.
- ELA detects compression history, not intent. A region re-saved at a different
  quality is flagged even if the change was a harmless export.
- Copy-move misses some edits. Flat regions (sky, walls) have few ORB
  keypoints; rotation/scaling can reduce matches; block matching is limited.
- LSB checks only work on lossless images. JPEG compression destroys LSB
  payloads; a negative LSB result does not prove there is no steganography.
- EXIF is easy to forge or strip. Missing EXIF is common after social media
  and screenshots; an editor tag is not automatically malicious.
- No reverse geocoding. The tool stays offline; it provides coordinates and an
  OpenStreetMap link instead of a place name.
- No PRNU / CFA / deepfake model. Source-camera identification and AI-generated
  image detection are limited to metadata heuristics.
- Thresholds are empirical. They are documented and configurable but not
  trained on a large labelled corpus.
- Single-file analysis. No batch mode, case database, video or disk images.
- GPS link needs a browser and internet to display the map; the analysis
  itself remains offline.

29. VIVA QUESTIONS AND SHORT ANSWERS
===============================================================================
Q1. What is image forensics?
A. The process of determining the origin, authenticity and history of a digital
image using file, metadata and pixel evidence.

Q2. Why use SHA-256 instead of MD5?
A. SHA-256 is collision-resistant and is the primary integrity digest. MD5 and
SHA-1 are kept only for legacy compatibility.

Q3. What are magic bytes?
A. The first bytes of a file that identify its real format. They are more
reliable than the file extension.

Q4. What is EXIF?
A. A TIFF-style metadata block written by cameras and phones. It can contain
camera identity, lens, capture time, GPS and a thumbnail.

Q5. Can EXIF be trusted?
A. No. It can be edited or stripped easily. It is corroboration, not proof.

Q6. What is ELA?
A. Error Level Analysis. Re-save the image at a known JPEG quality and compare
the pixels. Regions with a different compression history often show a different
residual.

Q7. Why is ELA not proof?
A. Texture, sharp edges, denoising, resizing and earlier JPEG saves also create
residuals. It detects compression inconsistency, not intent.

Q8. How does your ELA detector reduce false positives?
A. It uses 16x16 blocks, a robust median+MAD threshold, a 9x9 local-density
filter, a minimum area, and a region-vs-ring contrast check. Thin edges do not
form dense regions.

Q9. What is copy-move forgery?
A. Copying a region and pasting it elsewhere in the same image, often to hide or
duplicate an object.

Q10. How is copy-move detected?
A. ORB/SIFT keypoints are matched with a ratio test and verified with RANSAC.
Matched points reveal duplicated regions. Block matching is a fallback for flat
areas.

Q11. What is LSB steganography?
A. Hiding data in the least-significant bit of pixel values. The visual change
is at most 1 level per channel.

Q12. What is a chi-square attack?
A. A statistical test on even/odd value-pair frequencies. Sequential LSB
replacement tends to equalise the pairs, producing a high p-value.

Q13. Why do LSB checks fail on JPEG?
A. JPEG is lossy and quantises DCT coefficients, which destroys most LSB
payloads. LSB checks are strongest on PNG/BMP/TIFF.

Q14. What is appended-data steganography?
A. Data hidden after a format's end marker (PNG IEND, JPEG FF D9, GIF 3B).
Viewers ignore it, but it can carry a ZIP, PDF or executable.

Q15. What is chain of custody?
A. A documented record of who handled the evidence, when, and what they did. The
hash chain makes tampering with the audit log detectable.

Q16. Why is the tool offline?
A. To avoid leaking evidence to third-party services and to keep the analysis
reproducible. GPS is shown as coordinates plus an OpenStreetMap link.

Q17. What is the final verdict formula?
A. Weighted score: file 0.15, metadata 0.20, ELA 0.20, copy-move 0.30, stego
0.15. Bands: <20 authentic, 20-49 suspicious, >=50 likely tampered.

Q18. What are the main limitations?
A. ELA false positives/negatives, copy-move misses flat regions, LSB checks fail
on JPEG, EXIF is forgeable, thresholds are empirical, and the tool is not
court-validated.

Q19. What is the future scope?
A. PRNU/CFA analysis, JPEG ghosts, deep-learning tamper localisation, C2PA,
batch/case database, signed PDF/A, video/deepfake detection and Autopsy/FTK
integration.

Q20. Why is the project modular?
A. Each analyzer is an independent pure function returning the same result
contract. This makes testing, tuning, reporting and future extension easier.
